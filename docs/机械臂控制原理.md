# Transbot 控制台机械臂控制原理（代码级拆解）

> 研究对象：`transbot_gui.py` 的“云台与机械臂”页。
> 结论先行：**GUI 不直接驱动电机，也不做运动学解算。它只是把“某个舵机 ID 转到某个绝对角度、用多少毫秒转过去”封装成 ROS 消息发出去；真正的位置闭环在总线舵机内部。**
>
> 本文的代码引用都能在本地核对；官方舵机 API 语义来自 Yahboom《Control bus servo》教程。
> 本仓库**没有** `Transbot_Lib.py` / `arm_transbot.py`；实测本机镜像上也不存在这两个文件，
> 驱动实际走 `~/transbot_ws/src/transbot_bringup/scripts/transbot_driver.py`（见第 4 节）。
> 因此“串口帧的具体字节”和“舵机内部 PID”只能标为推断。

---

## 0. 一句话原理

```text
控制机械臂 = 位置控制（Position Control）
           = 给每个关节的舵机发一个“绝对目标角度 + 运动时长”
           + 舵机自己用内部传感器闭环走到目标并保持
           + 需要时再通过另一个服务把真实角度读回来
```

这跟底盘完全不同：

| | 底盘 | 机械臂 |
|---|---|---|
| 指令含义 | 速度（m/s、rad/s） | 绝对角度（°） |
| 是否需要持续发 | 是，GUI 20 Hz 重发，停发可能保持上次速度 | 否，发一次就够，舵机自己走完并保持 |
| 反馈 | `/odom`、编码器 | `/CurrentAngle` 服务，按需查询 |
| 控制闭环在哪 | 底盘 MCU / 电机驱动器 | **舵机内部** |
| GUI 侧是否有闭环 | 没有，开环发速度 | 没有，开环发角度；读回只是人工校验 |

## 1. 三层架构

```text
┌──────────────────────────── VM（你的电脑） ────────────────────────────┐
│                                                                        │
│  Tk 滑块 / 按钮                                                         │
│      │                                                                  │
│      ▼                                                                  │
│  RobotGUI._send_arm_joint() / _send_arm_all()                           │
│      │  构造 transbot_msgs/Arm                                         │
│      ▼                                                                  │
│  RobotROS.arm()  ──publish──►  /TargetAngle  (Arm)                      │
│                                                                        │
│  读回：RobotROS.read_angles() ──call──► /CurrentAngle (RobotArm srv)    │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ WiFi / TCPROS
                                   │ master 只是花名册，数据是节点间直连
┌──────────────────────────────────▼─────────────────────────────────────┐
│                       机器人 Jetson（transbot_node）                    │
│                                                                        │
│  sub_armcallback(msg)                                                  │
│      for joint in msg.joint:                                           │
│          bot.set_uart_servo_angle(id, angle, run_time)                 │
│                                                                        │
│  RobotArmcallback(req)                                                 │
│      bot.get_uart_servo_angle_array()  → [id7, id8, id9]               │
│                                                                        │
│      │ /dev/ttyTHS1 @115200                                            │
│      ▼                                                                  │
│  底盘 MCU  ──总线寻址──►  总线舵机 id7 / id8 / id9  ──►  关节           │
│                                                                        │
│  云台走另一条路：/PWMServo → set_pwm_servo(1, angle) → PWM 舵机         │
└────────────────────────────────────────────────────────────────────────┘
```

关键点：

- **ROS master 不是数据中转站**，只负责“谁发布/订阅什么”的登记；真正的消息是
  VM 上的发布者和机器人上的 `transbot_node` 之间直接 TCP 传输。
- 所以 `ROS_MASTER_URI` 决定“去哪里登记”，`ROS_IP` 决定“机器人能不能反向连回你”。
  配错 `ROS_IP` 的典型症状是“看得见数据、但指挥不动”。
- GUI 端只 import `transbot_msgs`，**不 import** `Transbot_Lib`；因此它可以在 VM 上跑。
  真正碰硬件的只有机器人上的 `transbot_node`。

## 2. 硬件层：三个总线舵机 + 一个 PWM 云台

### 2.1 关节与舵机 ID

| 关节 | 舵机 ID | 作用 | 当前控制范围 | 官方手册范围（历史） | 反馈 |
|---|---|---|---|---|---|
| 底座回转 | 7 | 整条手臂水平旋转 | **0 ~ 225°** | 0 ~ 225° | 可读回 |
| 升降/抬臂 | 8 | 肩关节上下 | **15 ~ 240°** | 30 ~ 270° | 可读回 |
| 夹爪 | 9 | 开合（一个舵机带动左右两个爪） | **60 ~ 180°** | 30 ~ 180° | 可读回 |
| 云台偏航 | 1 | 相机左右转 | 60 ~ 120° | PWM 0 ~ 180° | **无读回** |

> 官方范围来自 Yahboom《Control bus servo》：
> `set_uart_servo_angle(s_id, s_angle, run_time=500)`，
> `7:[0,225]`、`8:[30,270]`、`9:[30,180]`。
> 官方还把 180° 描述为“竖直向上/夹紧”的参考状态：id7/id8 角度减小是向下，增大是向上；
> 夹爪角度增大是夹紧，减小是松开。
>
> **2026-10-29 限位裁决**：控制端统一用最新 GUI 的
> j7 `0~225°`、j8 `15~240°`、j9 `60~180°`（用户确认）。旧手册的
> id8 `30~270°` 和旧 URDF 换算结果不再作为控制限位；本节表格保留官方值
> 只作历史对照。详见 `wallmark/docs/07-文档总览.md` 的 C7。

### 2.2 总线舵机 vs PWM 舵机

- **总线舵机（id 7/8/9）**：三根线（电源、地、信号）串在同一条总线上，每个舵机有唯一 ID。
  主控发一帧命令，帧里带 ID；对应舵机收到后执行。它内部有 MCU、位置传感器（电位器/编码器）
  和电机驱动，能**自己闭环**，也能把当前角度回传。
- **PWM 舵机（id 1/2）**：普通的 50 Hz PWM 信号，主控只发脉宽，舵机内部同样有位置闭环，
  但**没有数字回读通道**。所以云台只能“发命令 + 本地估计”，不能像机械臂那样读回真实角度。

### 2.3 舵机内部到底发生了什么

这是“原理”的核心。以“id7 从 90° 转到 150°，run_time=1000 ms”为例：

```text
主控发命令：ID=7, target=150°, time=1000ms
        │
        ▼
舵机内部 MCU 收到目标
        │
        ├─ 读当前位置（电位器/编码器）→ 例如 90°
        ├─ 误差 = 150° - 90° = 60°
        ├─ 按 time 生成一条速度/位置轨迹（常见是梯形或 S 曲线）
        ├─ PID 控制电机 H 桥，让实际位置跟随轨迹
        └─ 到达目标附近（死区内）后停止，但继续通电保持力矩
```

所以：

- **“角度”是舵机输出轴的绝对角度**，不是“转多少度”的相对量。
- **“run_time”是这次运动的持续时间/速度参数**，不是超时时间，也不是控制周期。
  官方说明：数值越小转得越快，单位 ms，最小 0。
- 舵机到位后**会持续保持位置**（扭矩使能）。这就是为什么机械臂松手不会掉下来。
  官方库还提供 `set_uart_servo_torque(enable)`，`enable=0` 可以卸掉扭矩用手掰，
  但本 GUI 没有暴露这个功能。
- 舵机内部闭环不等于 ROS 闭环：**ROS 侧发完就不管了**，不知道有没有到位。
  要确认到位，必须另外调 `/CurrentAngle` 读回。

> 具体串口帧的字节格式（帧头、ID、命令字、校验和）在机器人上的
> `arm_transbot.py` / `Transbot_Lib.py` 里，本地仓库没有。上面是这类总线舵机的通用工作方式，
> 不是对具体帧格式的猜测。

### 2.4 角度坐标不是 URDF 弧度

URDF 里关节用弧度，舵机用“度”，而且不同关节有偏移和缩放。官方 MoveIt 适配脚本
`~/software/transbot_library/src/transbot_description/scripts/03_machine_move.py:28-44`
给出了精确换算（Astra 单轴云台，`len(msg.position) == 9`）：

```python
joints1 = camera_joint1 * 57.3 + 90          # PWM 云台 id1
joints2 = arm_joint1  * 57.3 + 225           # 总线 id7（底座）
joints3 = arm_joint2  * 57.3 + 45            # 总线 id8（升降）
joints4 = Jaws_joint  * 57.3 * 5 / 3 + 180   # 总线 id9（夹爪，额外 5/3 缩放）
bot.set_pwm_servo(1, int(joints1))
bot.set_uart_servo_angle_array(joints2, joints3, joints4)
```

对应关系：

| URDF 关节 | URDF 范围 | 换算 | 舵机角度 |
|---|---|---|---|
| `arm_joint1` 底座 | -225° ~ 0° | `×1 + 225` | 0 ~ 225° |
| `arm_joint2` 升降 | -15° ~ 225° | `×1 + 45` | **30 ~ 270°** |
| `Jaws_joint` 夹爪 | -91.7° ~ 0° | `×5/3 + 180` | 27.2 ~ 180° |
| `astra_joint` 云台 | -30° ~ +30° | `×1 + 90` | 60 ~ 120° |

这解释了两件事：

1. GUI 里说的“角度”是**舵机角度**，不是 URDF 弧度；它不需要 tf，也不需要逆运动学。
2. 旧 URDF 换算会得到 id8 `30~270`，但控制端采用实测/GUI 的 `15~240`；
   两者不一致是历史模型差异，**以 GUI 控制范围为准**，不要按旧换算去改 `ARM_LIMITS`。

## 3. ROS 层：消息与服务

### 3.1 消息定义

`vendor/transbot_msgs_src/msg/Arm.msg`：

```text
Joint[] joint
```

`vendor/transbot_msgs_src/msg/Joint.msg`：

```text
int32 id          # 7 / 8 / 9
int32 run_time    # 运动时长，单位 ms；0 会被驱动丢弃
float32 angle     # 目标绝对角度，单位度
```

`vendor/transbot_msgs_src/msg/PWMServo.msg`：

```text
int32 id          # 1 = 云台偏航
int32 angle
```

`vendor/transbot_msgs_src/srv/RobotArm.srv`：

```text
string apply      # 请求；服务端实际不用这个字段
---
Arm RobotArm      # 响应：三个关节的完整状态
```

### 3.2 话题 / 服务职责

| 名称 | 类型 | 方向 | 作用 |
|---|---|---|---|
| `/TargetAngle` | `transbot_msgs/Arm` | GUI → 机器人 | 下发 1~3 个关节的目标角度 |
| `/CurrentAngle` | `transbot_msgs/RobotArm` 服务 | GUI → 机器人 → GUI | 读回 7/8/9 的真实角度 |
| `/PWMServo` | `transbot_msgs/PWMServo` | GUI → 机器人 | 云台 PWM 舵机 |
| `/cmd_vel` | `geometry_msgs/Twist` | GUI → 机器人 | 底盘速度（与机械臂无关） |

为什么命令用 Topic、读回用 Service？

- 命令是“发出去就行”的异步动作，用 Topic 简单、低延迟；不需要等回应。
- 读回是“问一次、答一次”的查询，用 Service 才能拿到返回值。
- 但 Topic 是“尽力而为”，**没有送达确认**；Service 才有响应。

### 3.3 消息契约

ROS 话题传的是序列化后的二进制字节，两边的 `.msg` 定义必须逐字节一致（MD5 校验）。
`vendor/python/transbot_msgs/` 里是预生成的官方模块，所以 VM 不需要 catkin 编译也能 import；
机器人上的 `transbot_node` 用它自己那份 `transbot_msgs`。两边定义不一致时，ROS 会拒绝连接，
或者把字段解析成乱码。

## 4. 驱动层：机器人上的 `transbot_node`

文件：`~/transbot_ws/src/transbot_bringup/scripts/transbot_driver.py`

### 4.1 节点身份与硬件入口

```python
sys.path.append("/home/jetson/Transbot/transbot")   # 第 4 行
from Transbot_Lib import Transbot                   # 第 13 行
from arm_transbot import Transbot_ARM                # 第 15 行

self.bot_arm = Transbot_ARM()                       # 第 22 行
bot_arm_offset = self.bot_arm.get_arm_offset()       # 第 23 行
self.bot = Transbot(arm_offset=bot_arm_offset)       # 第 24 行
```

- 这个 `sys.path.append` 把驱动**钉死在机器人上**：VM 上没有
  `/home/jetson/Transbot/transbot`，import 会直接失败。
- `get_arm_offset()` 说明官方库启动时还会读一次机械臂安装偏移，传给 `Transbot`。
  也就是说底层可能对“名义角度”再加一次标定补偿；具体在机器人上的
  `arm_transbot.py` 里，本地看不到。
- 节点在 `bringup.launch:11` 里被命名为 `transbot_node`，并设置 `required="true"`：
  驱动一死，整个 launch 全部退出。

### 4.2 订阅、服务、初始化

```python
self.sub_TargetAngle = rospy.Subscriber("/TargetAngle", Arm,
                                        self.sub_armcallback, queue_size=10)   # 第 36 行
self.srv_CurrentAngle = rospy.Service("/CurrentAngle", RobotArm,
                                      self.RobotArmcallback)                   # 第 39 行
...
self.bot.set_uart_servo_angle(9, 90)                  # 第 49 行：启动时把夹爪设为 90°
```

> 注意第 49 行：**驱动节点启动时会主动把夹爪舵机转到 90°**。
> 这不是 GUI 发的，是驱动初始化的一部分；首次上电时夹爪可能会动一下。

### 4.3 机械臂命令回调

```python
def sub_armcallback(self, msg):
    if not isinstance(msg, Arm): return
    for joint in msg.joint:
        if not isinstance(joint, Joint): continue
        if joint.run_time != 0:
            self.bot.set_uart_servo_angle(joint.id, joint.angle, joint.run_time)
```

三个关键事实：

1. **驱动不检查角度限位**。它只判断 `run_time != 0`，然后原样下发。
   GUI 里的限位是“发送端安全边界”，不是驱动保证。
   任何其他 ROS 节点往 `/TargetAngle` 发超范围角度，都会被原样执行。
2. **`run_time == 0` 会被静默丢弃**：不报错，舵机就是不动。
3. 驱动是**逐条**调用 `set_uart_servo_angle` 的，不是官方的
   `set_uart_servo_angle_array`。所以一条 ROS 消息里带 3 个关节时，
   串口上是 3 条命令依次发，不是真正的一帧三轴同步。

### 4.4 角度读回回调

```python
def RobotArmcallback(self, request):
    response = RobotArmResponse()
    joints = self.bot.get_uart_servo_angle_array()   # [id7, id8, id9]
    for i in range(3):
        joint = Joint()
        joint.id = i + 7
        joint.angle = joints[i]
        joint.run_time = 500
        if joints[i] < 0:
            continue                                  # -1 表示该舵机没回复
        response.RobotArm.joint.append(joint)
    return response
```

- `i + 7` 是隐式契约：数组下标 0/1/2 → 舵机 ID 7/8/9。
- 某个舵机读失败时返回 `-1`，该关节会被**跳过**；所以读回结果可能只有 2 个关节。
- 响应里的 `run_time=500` 没有控制意义，只是把 `Joint` 字段填满。

### 4.5 云台回调

```python
def sub_PWMServocallback(self, msg):
    PWMServo_angle = int(msg.angle)
    if self.CameraDevice == "astra":
        if msg.id == 1:
            if PWMServo_angle <= 60: PWMServo_angle = 60
            elif PWMServo_angle >= 120: PWMServo_angle = 120
    if msg.id == 2:
        if PWMServo_angle > 140: PWMServo_angle = 140
    self.bot.set_pwm_servo(msg.id, PWMServo_angle)
```

- Astra 是单轴支架，所以 id1 被钳在 60~120；GUI 也用了同样的范围。
- 云台是 PWM 舵机，**没有 `/CurrentAngle` 读回**，只能本地估计。

## 5. GUI 层：代码逐段

文件：`transbot_gui.py`

### 5.1 ROS 接口初始化

```python
self.cmd_pub = rospy.Publisher('/cmd_vel', Twist, queue_size=2)
self.servo_pub = rospy.Publisher('/PWMServo', PWMServo, queue_size=10)
self.arm_pub = rospy.Publisher('/TargetAngle', Arm, queue_size=10)
self.rgb_srv = rospy.ServiceProxy('/RGBLight', RGBLight)
self.buz_srv = rospy.ServiceProxy('/Buzzer', Buzzer)
```

`/TargetAngle` 的 `queue_size=10` 是发送缓冲区深度；它不会让消息“保证送达”。

### 5.2 限位与关节名

```python
ARM_LIMITS = {7: (0, 225), 8: (15, 240), 9: (60, 180)}
ARM_NAMES = {7: '底座 (id7)', 8: '升降 (id8)', 9: '夹爪 (id9)'}
```

这里就是 GUI 的安全边界。`_send_arm_joint` 和 `_send_arm_all` 都会先检查
`lo <= angle <= hi`，不满足就拒绝发送并在日志里报错。

### 5.3 单关节发送

```python
def _send_arm_joint(self, jid):
    ang = int(self._arm_sliders[jid].get())
    lo, hi = self.robot.ARM_LIMITS[jid]
    if not (lo <= ang <= hi):
        ... 拒绝 ...
    cur = float(self._arm_cur.get(jid, ang))
    rt = self._arm_run_time(jid, ang, cur)
    self.cmd('arm', [(jid, ang, rt)], 1.0)
    self._arm_cur[jid] = ang
```

- `ang` 是滑块上的绝对角度。
- `cur` 是上一次“已知/估计”的角度，不是一个实时测量值。
- `rt` 是按角度差估的运动时长。
- **`_arm_cur` 在命令真正发出之前就被更新了**；如果发送失败，它会和真实角度漂移。

### 5.4 三轴一起发

```python
def _send_arm_all(self):
    joints, rts = [], []
    for jid in (7, 8, 9):
        ang = int(self._arm_sliders[jid].get())
        lo, hi = self.robot.ARM_LIMITS[jid]
        if not (lo <= ang <= hi):
            ... 跳过 ...
            continue
        rt = self._arm_run_time(jid, ang, float(self._arm_cur.get(jid, ang)))
        joints.append((jid, ang, rt))
        rts.append(rt)
        self._arm_cur[jid] = ang
    self.cmd('arm', joints, max(rts) / 1000.0 + 0.8)
```

- 它把 3 个 `Joint` 塞进**同一条 `Arm` 消息**，所以驱动会在同一个回调里依次处理。
- 但驱动是逐条调用 `set_uart_servo_angle` 的，不是 `set_uart_servo_angle_array`。
  所以“三轴同步”更准确的说法是：**几乎同时开始，各自按自己的 run_time 走完**，
  不是“同时到达”。如果要同时到达，需要统一 run_time 或由驱动发数组命令。

### 5.5 真正发布消息的地方

```python
def arm(self, joints, wait=1.5):
    with self._arm_lock:
        a = Arm()
        max_rt = 0
        for jid, ang, rt in joints:
            a.joint.append(Joint(id=int(jid), run_time=int(rt), angle=float(ang)))
            max_rt = max(max_rt, int(rt))
        deadline = time.time() + 1.5
        while (self.arm_pub.get_num_connections() == 0
               and time.time() < deadline and not rospy.is_shutdown()):
            time.sleep(0.05)
        self.arm_pub.publish(a)
        time.sleep(max(wait, max_rt / 1000.0 + 0.8))
```

四个设计点：

1. **`_arm_lock` 串行化**：连点多个命令会排队，避免后一条打断前一条。
2. **等订阅者连上**：最多等 1.5 秒，避免“发布时机器人还没连上，第一包丢了”。
   旧代码用“发两次隔 0.15 秒”补首包，但驱动每条都执行，结果动作被触发两遍；
   现在改成等连接再发一次。
3. **只发一次**：因为这是位置控制，不是速度控制。
4. **发完 sleep**：`max(wait, max_rt+0.8)` 是 GUI 侧的节奏控制，避免下一条命令
   在上一条还没走完时插进来。它不是“到位确认”，只是按时间等。

> 这也是为什么日志里的“✓ 指令已下发”会在动作时间之后才出现：
> `cmd()` 里的 `fn(*a)` 就是 `arm()`，它要 sleep 完才返回，然后才记日志。
> 这条日志只代表“消息已经 publish 过”，不代表“舵机已经到位”。

### 5.6 run_time 的算法

```python
@staticmethod
def _arm_run_time(jid, target, current):
    span = max(0, current - RobotROS.ARM_LIMITS[jid][0])
    ratio = abs(target - current) / float(max(1, span))
    return int(max(400, min(1500, 400 + ratio * 900)))
```

- 结果被限制在 **400 ~ 1500 ms**。
- 角度差越大，`rt` 越大，舵机转得越慢（官方语义：时间越小越快）。
- 但分母用的是 `current - 下限`，不是整个行程，也不是 `max(1, abs(target-current))`。
  这会导致同样的角度差，在靠近下限时算出更长的 `rt`，靠近上限时算出更短的 `rt`。
  它是一个**经验节奏**，不是物理速度模型。
- 举例：id7 当前 90°，目标 150°：
  `span = 90`，`ratio = 60/90 = 0.667`，`rt = 400 + 600 = 1000 ms`。
- 举例：id8 当前 15°（下限），目标 240°：
  `span = max(0, 0) = 0` → `max(1, 0) = 1`，`ratio = 225` → 被截到 1500 ms。
  225° 用 1.5 秒走完，速度是很快的；这就是为什么大角度动作要特别小心。

### 5.7 读回并回填滑块

```python
def _read_arm_and_log(self):
    r = self.robot.read_angles()
    joints = getattr(getattr(r, 'RobotArm', r), 'joint', [])
    ...
    def _sync():
        for j in joints:
            sl = self._arm_sliders.get(int(j.id))
            if sl is not None:
                sl.set(int(round(float(j.angle))))
    self._ui(_sync)
```

- `read_angles()` 在 `RobotROS` 里：
  ```python
  proxy = rospy.ServiceProxy('/CurrentAngle', RobotArm)
  rospy.wait_for_service('/CurrentAngle', timeout=3.0)
  return proxy(apply='')
  ```
- 返回的 `RobotArm.joint` 可能少于 3 个（读失败的关节被驱动跳过）。
- **回填只改了滑块，没有更新 `self._arm_cur`**。这是一个真实的 bug：
  读回后，下一次 `_arm_run_time` 仍然用旧缓存算时长，可能算得太短或太长。
- 连接建立时 `_ros_connect()` 会先直接读一次，再 `cmd('read_arm')` 读一次
  （`transbot_gui.py:2643-2652`），实际上是两次服务调用，第一次结果被丢弃。

### 5.8 云台发送

```python
def servo(self, sid, angle):
    angle = self._clamp(angle, 60, 120) if sid == 1 else self._clamp(angle, 0, 140)
    self.servo_pub.publish(PWMServo(id=sid, angle=angle))
```

- 云台 id1 在 GUI 和驱动两层都被钳到 60~120。
- GUI 只暴露 id1（Astra 单轴，没有俯仰舵机）。
- 驱动侧对 id2 还有 140° 上限，但 GUI 不发 id2。

### 5.9 命令为什么在后台线程

```python
def cmd(self, kind, *a):
    ...
    def wrap():
        try:
            r = fn(*a)
            ...
        except ...
    threading.Thread(target=wrap, daemon=True).start()
```

- `arm()` 里有 `time.sleep(...)`，`read_angles()` 可能阻塞，`cmd()` 还可能有网络等待。
  这些都不能放在 Tk 主线程，否则界面会卡死。
- 后台线程只做 ROS IO；所有 Tk 控件更新都通过 `_ui()` 队列回到主线程
  （`transbot_gui.py:2658-2675`），因为 Tk 不是线程安全的。

## 6. 一次“发送”从点击到关节转动的完整生命周期

以“底座 id7 从 90° 转到 150°”为例：

1. 你拖动滑块到 150°，点“发送”。
2. `_send_arm_joint(7)` 读取滑块值 150，检查 `0 <= 150 <= 225`。
3. `_arm_cur[7]` 假设是 90；`_arm_run_time(7, 150, 90)` 算出 1000 ms。
4. `cmd('arm', [(7, 150, 1000)], 1.0)` 检查 `STATE['ok']`，然后启动后台线程。
5. 后台线程调用 `RobotROS.arm()`，拿到 `_arm_lock`，构造：
   ```text
   Arm.joint[0] = Joint(id=7, run_time=1000, angle=150.0)
   ```
6. `arm()` 最多等 1.5 秒，直到 `/TargetAngle` 有订阅者；然后 `publish`。
7. rospy 把消息序列化，通过 TCP 发给机器人上的 `transbot_node`。
8. `sub_armcallback` 收到消息，检查 `run_time != 0`，调用
   `bot.set_uart_servo_angle(7, 150.0, 1000)`。
9. `Transbot_Lib` 通过 `/dev/ttyTHS1`（115200）把总线命令发给底盘 MCU，
   MCU 再寻址 id7 舵机。
10. 舵机内部闭环：读当前位置 → 按 1000 ms 生成轨迹 → 驱动电机 → 到位后保持。
11. GUI 在 `arm()` 里 `sleep(max(1.0, 1.0+0.8)) ≈ 1.8 s`，然后打印
    “✓ 机械臂 指令已下发”。
12. 如果你点“读取当前角度”，GUI 调 `/CurrentAngle`，驱动读
    `get_uart_servo_angle_array()`，把 id7/8/9 的真实角度返回；滑块被回填。

注意：

- 第 11 步的日志不是“到位确认”，只是“发完并等了一会儿”。
- 网络延迟、串口延迟、舵机启动延迟都包含在这条链路里；`run_time` 只覆盖舵机内部运动时间。
- 如果第 7 步时机器人离线，消息可能被丢弃；GUI 的 `STATE['ok']` 不会立刻变成 False，
  所以日志仍可能显示“已下发”。

## 7. 几个最容易误解的点

### 7.1 为什么机械臂发一次就够，底盘要一直发？

- 机械臂 `/TargetAngle` 是**位置设定值**：舵机内部记住目标，自己闭环，到了就保持。
- 底盘 `/cmd_vel` 是**速度设定值**：底盘 MCU 按最后收到的速度持续驱动电机；
  如果不再发，它可能一直按上次速度走。GUI 因此用 20 Hz 重发 + 超时自动停车
  （`transbot_gui.py:599-639`）。
- 这也是为什么机械臂重复发同一条命令通常不会出问题（只是重新设定同一个目标），
  而底盘重复发/漏发会直接影响运动。

### 7.2 “三轴同步”到底同步了什么？

- GUI 把 3 个 `Joint` 放进**同一条 ROS 消息**，所以它们几乎同时到达驱动。
- 驱动 `sub_armcallback` 是 `for joint in msg.joint:` **逐条**调用
  `set_uart_servo_angle`，不是 `set_uart_servo_angle_array`。
- 每条命令有自己的 `run_time`，所以三个关节**几乎同时开始，但按各自时长结束**。
- 真正的“同时到达”需要：
  - 给三个关节相同的 `run_time`，或
  - 驱动改用 `set_uart_servo_angle_array(angle7, angle8, angle9, run_time)`，或
  - 上层做轨迹规划，按时间切片连续下发。
- 官方 `set_uart_servo_angle_array` 确实存在（《Control bus servo》），
  但当前 ROS 驱动没有用它。这是一个可以改进的点。

### 7.3 闭环到底在哪？

```text
舵机内部：位置闭环（电位器/编码器 → PID → 电机）  ✅
ROS 驱动：开环（publish 后不管）                  ❌
GUI：     开环（只缓存上次目标，不自动读回）        ❌
```

所以“机械臂控制”并不是 ROS 在实时控制，而是**ROS 把目标告诉舵机，舵机自己控制自己**。
`/CurrentAngle` 只是一个“事后测量”的查询接口，不参与控制。

### 7.4 为什么 GUI 不需要逆运动学（IK）？

- GUI 控制的是**关节空间**：每个滑块直接对应一个舵机角度。
- 它不关心“机械臂末端在笛卡尔空间的 x/y/z”，所以不需要 IK、不需要 tf、不需要 MoveIt。
- 如果你想让末端走到某个坐标，才需要：
  MoveIt 规划 → `/joint_states` → `03_machine_move.py` → 舵机角度。
  官方 MoveIt 示例走的就是这条路；控制台 GUI 走的是更直接的遥控路径。
- 两条路的底层终点是一样的：`set_uart_servo_angle` / `set_uart_servo_angle_array`。

### 7.5 URDF、RViz 和真实机械臂的关系

- URDF 描述的是几何、关节轴、限位，用于 RViz/MoveIt 的可视化和规划。
- `bringup.launch` 里的 `joint_state_publisher` 发布的是**默认/仿真关节状态**，
  不是 `/CurrentAngle` 的真实读数。
- 所以 RViz 里看到的机械臂姿态**不一定等于真实机械臂姿态**，除非你额外把
  `/CurrentAngle` 转成 `sensor_msgs/JointState` 喂给 `robot_state_publisher`。
- GUI 里的限位以真机控制口径为准（2026-10-29 确认），不再由旧 URDF 反推；
  GUI 本身不做任何 URDF 计算。

## 8. 安全边界与代码问题

### 8.1 限位口径（2026-10-29 已裁决，不再按旧手册改）

```python
ARM_LIMITS = {8: (15, 240)}     # 当前控制口径（GUI / 真机）
# 官方手册：set_uart_servo_angle(8, angle)  angle ∈ [30, 270]
# 旧 URDF + MoveIt 换算：arm_joint2(-15°~225°) + 45 → [30, 270]
```

- 当前控制端统一用 **j7 0~225°、j8 15~240°、j9 60~180°**（用户确认）。
- 官方手册的 id8 `30~270` 与旧 URDF 换算是历史资料，**不再作为控制限位**；
  不要据此把 `ARM_LIMITS[8]` 改回 `(30, 270)`。
- 夹爪的 60~180 比官方 30~180 保守，属于“少开一点”，通常安全，但会损失开口范围。
- 无论限位怎么写，第一次动臂都应小步、空载、有人看护；见 9.3 的安全实验建议。

### 8.2 高优先级：驱动不限制机械臂角度

- `sub_armcallback` 只检查 `run_time != 0`，不检查 `angle` 范围。
- GUI 的限位是唯一的保护；任何其他 ROS 节点（或命令行 `rostopic pub`）都能绕过。
- 对比：云台在驱动里有 60~120 的钳制，机械臂没有。
- **结论**：不要把这套系统当成“驱动一定安全”；安全边界在发送端。

### 8.3 中优先级：`_arm_cur` 不是测量值

- `_arm_cur` 初始是 `{7: 90, 8: 100, 9: 150}`（`transbot_gui.py:1390`），
  连接后会读一次真实角度，但**读回只更新滑块，不更新 `_arm_cur`**。
- 如果机械臂被手动掰动、或某次命令失败，`_arm_cur` 会和真实角度脱节。
- `_arm_run_time` 用这个缓存算时长，可能导致动作过快或过慢。
- **建议**：在 `_read_arm_and_log` 的 `_sync()` 里加上
  `self._arm_cur[int(j.id)] = float(j.angle)`；并且只在 publish 成功后更新缓存。

### 8.4 中优先级：没有机械臂急停 / 扭矩开关

- GUI 的“紧急制动”只发 `/cmd_vel = 0`，停的是底盘，不是机械臂。
- 关闭窗口时 `_on_close()` 只调用 `stop_manual()` 停底盘；机械臂会保持最后一个目标，
  舵机继续通电保持力矩。
- 如果发生危险，最快的方式是断开机械臂电源/急停（硬件），而不是点 GUI。
- 官方库有 `set_uart_servo_torque(0)` 可以卸扭矩，但 GUI 没有暴露。

### 8.5 中优先级：日志不是到位确认

- “✓ 指令已下发”出现在 `arm()` sleep 之后，只代表 publish 过。
- 没有自动读回校验；是否到位要靠“读取当前角度”按钮人工确认。
- `STATE['ok']` 在连接成功后一直为 True，没有心跳；机器人中途掉线时，
  GUI 仍可能显示“已连接”，命令被静默丢弃。

### 8.6 低优先级：读回可能缺关节

- 驱动对 `get_uart_servo_angle_array()` 返回 `-1` 的关节直接跳过。
- GUI 只更新返回了的关节滑块；缺失的关节保持旧值，看起来像“读到了”，其实是 stale。
- 如果某个舵机线松了/ID 冲突，读回会少一个关节，但界面不会明显报错。

### 8.7 低优先级：`run_time` 的经验公式不物理

- 分母 `current - lo` 会导致同样的角度差在不同位置得到不同的时长。
- 400~1500 ms 的硬限制意味着大角度动作可能仍然很快。
- 它不是速度/加速度规划，不会限制电流、不会做 S 曲线；真正的轨迹在舵机内部。

### 8.8 信息：RViz 里的手臂可能是“假”的

- `bringup.launch` 的 `joint_state_publisher` 发布默认关节状态，
  不是真实舵机角度。
- 所以 RViz 里的手臂姿态不能当作实机姿态；要真实同步，需要把
  `/CurrentAngle` 转成 `JointState` 发布。

### 8.9 信息：启动时夹爪会动

- `transbot_driver.py:49` 在节点初始化时执行 `set_uart_servo_angle(9, 90)`。
- 这不是 GUI 发的；每次启动 `transbot_node` 都可能把夹爪转到 90°。
  调试时手不要放在夹爪里。

## 10. 总结

把整条链路压缩成一句话：

> **Tk 滑块 → `Arm/Joint` 消息 → `/TargetAngle` → `transbot_node` →
> `set_uart_servo_angle(id, angle, run_time)` → `/dev/ttyTHS1` → 底盘 MCU →
> 总线舵机内部位置闭环 → 关节到位并保持；`/CurrentAngle` 是另一条读回通道。**

需要记住的四个关键词：

1. **位置控制**：发绝对角度，不是速度；发一次就够。
2. **舵机内部闭环**：ROS 侧是开环，真正的 PID 在舵机里。
3. **run_time 是运动时长/速度参数**：不是超时，0 会被驱动丢弃。
4. **关节空间**：GUI 不做 IK；要笛卡尔控制请走 MoveIt。

最值得核对的两个问题：

- `ARM_LIMITS[8] = (15, 240)` 与官方 `[30, 270]` 不一致，下限有堵转风险。
- 读回只更新滑块、不更新 `_arm_cur`，会导致 `run_time` 估算失真。
