# slam_nav — 边建图边导航（独立工具）

gmapping 一边建图，move_base 直接在**实时地图**上规划。没有 map_server，也没有
amcl：位姿来自 gmapping 的 `map→odom`。

这个目录是**自包含**的，不改 `map_gui`（纯建图）也不改 `task_gui`（画线任务）。

```
slam_nav.launch     gmapping + move_base（move_base 发 /cmd_vel_raw）
slam_nav_gui.py     实时地图 + 点地图发目标（map_gui 的副本，导航常开）
start_slam_nav.sh   一键启动：扫描滤波 → 建图+导航 → 角速度补偿 → 窗口
```

## 跑

```bash
cd ~/transbot/wall_task/slam_nav
./start_slam_nav.sh --dark
```

启动前会**停掉** map_server / amcl / move_base / gmapping——否则会有两个 `/map`
发布者和两个 `map→odom`，两边都坏。关窗口会把它们一起停掉。

## 操作

- **左键点地图 = 发目标**（要求周围 0.30 m 都是已知空闲，点未知区域会被拒绝）
- **右键 = 取消目标**
- 拖动 = 平移，滚轮 = 缩放，双击 = 复位
- 「启用遥控」勾上后 WASD 可以手动开

**遥控和导航互斥**：两者都会往 `/cmd_vel` 写，同时开的话驱动收到的是两路交错
指令，走起来一卡一卡。所以：

- 勾遥控 → 先取消导航目标，遥控接管
- 点地图发目标 → 自动关掉遥控

不需要手动去关另一个，谁最后动谁说了算。

## 这套方案固有的毛病（不是 bug）

| 现象 | 原因 |
|---|---|
| 车会频繁重新规划、走走停停 | 地图每 1 s 更新一次，路径不断作废 |
| 到达目标后位置有点飘 | 回环闭合时 `map→odom` 会跳，目标在世界里的位置跟着变 |
| 不能规划到没扫过的地方 | 未知区不可通行；界面直接拒绝这类目标 |
| 建出来的图不如专门建图干净 | 边走边建，扫描重叠少、回环少 |

## 验证状态

- ✅ 栈能起来：`/scan_filtered` 7.3 Hz、gmapping 出图、move_base 在线、
  `/cmd_vel` 经过 0.709 补偿
- ✅ 位姿来自 TF（`map→base_footprint`），界面显示正常
- ✅ 点地图发目标的完整闭环：真车跑过，move_base 接受
  `/move_base_simple/goal` 并开动
- ⬜ 回环跳变时的表现没测——见下一节

## 回环跳变是什么

gmapping 手上只有里程计，走久了误差会累积。当车绕回来、重新看到走过的地方，
扫描匹配认出"这两帧是同一堵墙"，就把累积误差一次性摊掉，发一个 `map→odom`
的阶跃修正。这就是 loop closure jump。

界面上看到的是：**车其实没动，但地图整体挪了一下**，连带车在地图上的位置、
走过的轨迹一起跳，量级几厘米到几十厘米、几度。这套方案没有 amcl，`map→odom`
是唯一位姿来源，所以这个修正会直接生效。

对点目标的影响：目标是 `map` 坐标系里的一个固定点——`slam_nav_gui` 只发一次
`/move_base_simple/goal`，`self.goal` 存的就是地图坐标。跳变后地图原点相对
真实世界变了，同一个地图坐标对应的物理位置也跟着偏同样的量，move_base 于是
朝"偏了的那一点"重新规划，表现为快到点了又倒回去或者横移一段。

怎么看出来：

- 界面上地图整体平移/旋转一下，蓝色轨迹在那里折一下
- `rosrun tf tf_echo map odom` 的平移或 yaw 出现阶跃（正常应该是缓慢连续变化）
- 绕一圈回到起点附近时最容易触发

要量化就得同时录 `/tf`（map→odom）和 `/odom`，把跳变时刻的阶跃减去同期里程计
增量——差值才是真正的修正量。

## 一个已知行为

gmapping 的 `temporalUpdate` 是 −1、`linearUpdate` 0.1 m：**车不动就不更新地图**。
所以刚启动时 `/map` 只有一帧，看起来是放射状条纹，开起来才会填满。
