# task_gui — 一个窗口跑完「导航 → 对准 → 画线」

导师的任务：导航到墙面附近 → 确认目标墙 → 机械臂夹笔在墙上画一条竖线。
这个目录就是那条流水线，一条命令启动。任务目录现已并入 `transbot/wall_task/`。

## 文件

| 文件 | 作用 |
|---|---|
| `task_gui.py` | 主窗口：阶段切换、地图、相机、手柄、机械臂、画线 |
| `arm_client.py` | 机械臂：读 `/CurrentAngle`、慢速摆位、笛卡尔闭环画线 |
| `mapdata.py` | 读 map_server 的地图、坐标换算、通行性检查（无 Tk 依赖，可单测） |
| `start_task.sh` | **一键启动**：六步自检完再开窗口 |
| `start_task_en.sh` | 同上，英文界面（`--lang en`） |
| `run_task_gui.sh` | 一行转发到 `start_task.sh`，旧笔记里的命令还能用 |

几何用 `../wallline/line_tool.py`（`arm/line_tool.py` 的副本，加了"从上往下画"）。

## 跑

```bash
cd ~/transbot/wall_task/task_gui
./start_task.sh                 # 找机器人 -> 自检 -> 校时 -> 起导航栈 -> 开窗口
./start_task.sh --stage align   # 直接进某个阶段
./start_task.sh --no-nav        # 不自动起导航栈
./start_task.sh --offline       # 不连机器人，只看界面
./start_task_en.sh              # 英文界面
```

启动前按顺序做六件事，每件都打印结果：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 1 找机器人 | `$ROBOT_IP` → 配置文件 → mDNS → 扫 `:11311` → 默认 | 控制机 DHCP 换段后不用改代码 |
| 2 ROS 环境 | source `console/env.sh`，再用发现的地址覆盖 | 顺带拿到 `transbot_msgs` 和各 workspace |
| 3 机器人自检 | 杀旧窗口和孤儿记录器；串口只有一个写者（否则杀 `transbot_main`）；清 `/task_gui_*` 僵尸；杀 `/TransbotPatrol`、`/BigTransbot`；**读电池电压** | 两个写者 → MCU 收交错帧；僵尸注册 → 驱动反复拨死地址；电压低 → 只出 25% 速度，像"没反应" |
| 4 时钟 | 一次往返补偿同步 + 起守护进程 | 偏差过 `transform_tolerance` 后 AMCL 停发，像"箭头冻住" |
| 5 导航栈 | 缺节点就起；**挂在旧 IP 上就重启**；起完再验：三个节点地址、`/cmd_vel` 订阅者、残留目标 | 名字对、地址错是最隐蔽的"全 ok 但不动" |
| 6 窗口 | `exec task_gui.py` | |

## 三个阶段

三个阶段抢同一个 `/cmd_vel` 和同一台机器人，所以用状态机卡住：

| 阶段 | 允许 | 禁止 |
|---|---|---|
| 1 导航 | 点地图发目标、设初始位姿、相机启停 | 手柄、机械臂 |
| 2 对准 | 手柄、相机、激光、机械臂手动三关节 | 地图点击（点了会提示） |
| 3 画线 | 机械臂、画线参数 | 手柄、地图点击 |

切到 2 或 3 会**先取消 `move_base` 目标**，否则一边点地图一边推手柄，两个发布者打架。

## 联锁

- 画线前查 `move_base` 不在 active
- 画线前查**笔尖离起点 1.5 cm 内**，否则 `draw_points()` 会从当前位置直接跳到起点
- `z 止` 低于 −5.5 cm（台面安全线）直接拒绝
- 松键、窗口失焦、按 ESC、关窗口全部发零（驱动没有命令超时）
- 导航目标离障碍 ≥0.45 m（臂伸出 27 cm，雷达 13 cm 高看不见它）

## 演示流程

1. 阶段 1 点地图，目标选在墙前 0.5 m 左右
2. 阶段 2：读「激光」，按「取距离」把距离填进阶段 3（自动加 15.9 cm 雷达→j7 偏移）
3. 手柄慢慢往前推，笔尖快贴墙时停
4. 阶段 3：按「校验」看 d 和 z 在不在可画区间，按「摆到起点」
5. 「开始画线」→ 从上往下 21.5 cm
6. **「退 1 cm 离墙」**，然后才回阶段 1 倒车

## 阶段 1：目标怎么给

| 操作 | 结果 |
|---|---|
| 单击地图 | 目标点；朝向默认取"从机器人指向目标"的方向 |
| Shift + 单击 | 朝向固定 0（地图 +x），调试用 |
| 勾「指定目标朝向」后点两下 | 第一下位置，第二下朝向；地图上画成箭头 |

**为什么必须能指定朝向**：DWA 一定会停在某个 yaw 上，以前那个 yaw 是最后一段
碰巧的方向。贴墙任务里终点朝向才是关键——车要正对墙，笔才是垂直的。

## 阶段 1：导航用的是什么算法

| 层 | 算法 | 参数 |
|---|---|---|
| 全局 | `global_planner/GlobalPlanner`，Dijkstra（`use_dijkstra: true`）在全局代价地图上搜 | 0.05 m 栅格、`inflation_radius 0.45`、`cost_factor 0.55`、`use_grid_path: false`（梯度下降平滑）、`orientation_mode: 0`（路径点不带朝向） |
| 局部 | `dwa_local_planner`，每 0.1 s 采样 15×30 组 (v, ω)，前向仿真 2 s | `path_distance_bias 32`、`goal_distance_bias 20`、`occdist_scale 0.03` |

全局路径 1 Hz 重算一次（`planner_frequency: 1.0`）。

**为什么车会不停摆方向**，三个原因叠在一起：

1. **DWA 没有"保持航向"这一项。** 它评的是"轨迹终点离全局路径多远"，不是
   "车头对不对着路径切线"。平行但偏一点、和斜着但更近，得分可能差不多，
   每 0.1 s 独立选一次，接近平局时符号会翻。
2. **底盘执行不了小角度。** 实测角速度死区约 0.15 rad/s、量化 0.01、增益 1.41。
   DWA 典型修正量是 0.03~0.08 rad/s（实测中位数 0.036），落进死区等于没发；
   误差攒到超过 0.15 才真转，而真转又是 1.4 倍速 → 过冲 → 反向修正。
3. **到点还要转一下。** `latch_xy_goal_tolerance: true` + `yaw_goal_tolerance 0.15`，
   进了 12 cm 就只原地转到目标 yaw，看起来就是"停了又扭一下"。

**已做的两处补偿（2026-11-05 实测）**：move_base 现在发 `/cmd_vel_raw`，
`cmd_vel_scale.py` 乘 0.709 再发 `/cmd_vel`，把底盘 1.41 倍的角速度增益抵掉；
`min_vel_x` 改成 0，禁止倒车。两次实跑：倒车 21% → **0%**，实际转角/计划转角
140% → **102~104%**。注意 GUI 手柄不经过补偿节点（手动微调比显示值快 40%）。

想真正"正对路线走"，得换局部控制器（纯跟踪 + 死区感知的 bang-bang 转向），
DWA 调参只能减轻。建图时用的 `HeadingHold` 实测 20 次转向误差 < 1.01°、
直线 1.4 m 漂 0.9°，就是这套思路。

## 全是 ok 但不动，先看这两个

| 检查 | 现象 | 处理 |
|---|---|---|
| 状态栏电压 | < 11 V 会显示 `!!` | 充电到 12 V。实测 10.3 V 时 0.2 m/s 指令只走 0.05 m/s，0.05 m/s 只走 2 mm，看起来就是"按了没反应" |
| 节点地址 | `rosnode info /move_base` 里的 `http://` 不是本机 IP | 启动脚本第 5 步会自动发现并重启；手动是 `pkill -f move_base` + `rosnode cleanup` + `start_nav.sh` |

地址这条特别隐蔽：`rosnode list` 只看名字，节点明明在，但它的 XML-RPC 还宣告着
上一次 DHCP 给的地址。机器人驱动每次连 `/scan`、`/odom` 都往那个死地址拨号，
命令就进不来。

## 记录模式

导航阶段按「记录」开始，再按一次停止。报告写到
`~/.local/share/transbot/wall_task/traces/<时间戳>/`：

| 文件 | 内容 |
|---|---|
| `report.md` | 时间分布 + 时间线（每段标行为与原因）+ 异常 |
| `trace.csv` | 10 Hz 原始表，每行带 `label` 和 `reason`，可以拿去做图 |

命令行也能跑，不依赖界面：

```bash
source ~/transbot/console/env.sh
python3 ~/transbot/wall_task/tools/nav_trace.py --duration 60
python3 ~/transbot/wall_task/tools/nav_trace.py --selftest   # 不连 ROS，验分类逻辑
```

它把「指令」和「实际」对起来判断，所以能回答"为什么它突然倒车/转圈"：

| 判据 | 结论 |
|---|---|
| `v < -0.02` | 倒车 |
| `|v| < 0.02` 且 `|ω| > 0.05` | 原地转 |
| 离目标 < 0.17 m 还在转 | 到点原地转到目标朝向（latch） |
| 车头与路径夹角 > 20° 且在转 | 先原地对齐 |
| 指令 0.15、实测 0.04 | 底盘没跟上（死区/堵转） |
| ω 在 1 秒内换向 ≥ 4 次 | 极限环 |
| AMCL 单次跳 > 5 cm 或 3° | 定位修正 |

记录器是**独立进程**：它有自己的订阅和时间线，杀掉它不会影响 move_base。
所以演示时也可以一直开着，出问题回头再看。

## 阶段 1：搬动之后怎么恢复定位

AMCL 无法从"被搬走 2 米"里恢复，粒子全在旧位置。两个入口：

| 入口 | 做法 | 什么时候用 |
|---|---|---|
| 重新定位 | 跑 `coarse_localize.py` 全图似然场搜索，结果发 `/initialpose` | 小范围挪动 |
| 设初始位姿 | 勾上后在地图上点两下：先点位置，再点朝向 | **首选**，尤其搬动过 |

自动搜索在这个长方形实验室里有 180° 孪生解：实测两次分别给
(0.40, 2.55, 105°) 和 (0.00, 2.55, 47°)，yaw 差近 60°，似然只差 0.08。
所以搬动之后别信自动结果，点两下最稳。

## 阶段 2：手柄

十字排布：↑↓ 前后、←→ 左右转、中间停。`w/s` 前后、`a/d` 转、`q/e` 横移。

单击也会动：按下到松开不足 0.25 s，命令会保持 0.25 s 再停（约 2.5 cm），
否则一次点击短于 50 ms 的刷新周期，看起来像没反应。

## 阶段 2：机械臂手动三关节

`j7 [ ] j8 [ ] j9 [ ] [读当前] [发送]`。j9 是夹爪，**夹笔用 158~160**。

- 发送时 `run_time = clamp(最大角度差 × 20 ms, 400, 3000)`
- 输入框首次从实测姿态填充，**等三个关节都回来才填**——总线偶尔只回两个
- 越界直接拒绝，不发送

## 阶段 2：相机

驱动只发原始图 `/camera/rgb/image_raw`（约 7 fps），`/compressed` 话题在
master 上是个僵尸注册，没有节点发布。所以订阅原始图，`rgb8` 直接 reshape
成 PIL，不需要 cv_bridge。

「相机开 / 相机关」走 sshpass 到机器人上清残留进程再
`roslaunch astra_camera astrapro.launch`。两个坑：

- `astra_camera` 包在 `~/software/transbot_library` 里，必须 source 那个
  workspace，否则报 "neither a launch file in package [astra_camera]"
- `pkill -f` 的 pattern 要用 `[a]stra_camera` 方括号写法，否则会匹配到
  承载这条命令的 ssh 会话本身，把自己杀掉

## 阶段 3：画线参数

`d = 26.2 cm`，`z 起 +16.0` → `z 止 −5.5`，线长 **21.5 cm**。z 相对 j7 轴，
j7 轴离安装面 8.0 cm，所以下端是底座上方 2.5 cm。

- 起点 j7=167.0 / j8=123.7（笔倾角 +15.7°，臂展 30.7 cm）
- 终点 j7=146.4 / j8=94.9（笔倾角 −33.7°，臂展 26.8 cm）
- `z=+18.3` 是臂展极限，接近奇异点，别再往上加

画线是**笛卡尔闭环**：实测姿态 FK → 投影到路径 → 往前看 1.2 cm → IK → 发送；
停住时前视涨到 2.5 cm。不是关节空间的绝对角度点——那样 1 cm 步长只有 1.6°，
落在舵机死区里，机械臂根本不动。

## IP

**机器人**是热点 AP，固定 `192.168.1.11`。

**控制机的 WiFi 已固定成 `192.168.1.136`**（2026-11-04 设置）：

```
NetworkManager 里三个同名 "Transbot" 配置（每点一次 SSID 就多一个）
  → ipv4.method manual / 192.168.1.136/24 / never-default yes
  → "Transbot" 的 autoconnect-priority 10
```

`never-default` 是必要的：否则连上机器人热点后，默认路由会被抢到那个没有
外网的口上。

固定之后，"节点挂在旧地址"那一类问题从根上消失——`ROS_IP` 恒为 `.136`。
启动脚本仍保留地址自检，作为配置被改回去时的兜底。

配置被重置（例如又在网络菜单里新建了一个 `Transbot 1`）时，一条命令恢复：

```bash
sudo bash ~/transbot/wall_task/tools/fix_control_ip.sh          # 默认 192.168.1.136/24
sudo bash ~/transbot/wall_task/tools/fix_control_ip.sh 192.168.1.50/24
```

**VMware NAT 那一侧（`192.168.240.x`）仍是 DHCP**，会在 `.145`/`.146` 之间变。
它只影响从 Windows SSH 进控制机，不影响 ROS（ROS 走 WiFi 那张网卡）。
要固定它需要管理员权限给 VMware 的 DHCP 加一条 host 保留，或者用 VMware
虚拟网络编辑器。

启动脚本仍会按 `$ROBOT_IP` → 配置文件（先探 `:11311`）→ mDNS → 扫网段 →
出厂地址 的顺序找机器人，找到的写回 `~/.config/transbot_console.conf`。

## 英文界面

```bash
./start_task_en.sh
```

和 `console/transbot_gui.py` 同一套做法：一张 `_EN` 表按中文字面量查，`T()` 翻译。
静态控件在界面搭好后由 `_translate_tree()` 统一翻一遍；运行时变的文本（状态栏、
读数、日志）在格式化处包 `T()`。

> 别把翻译函数叫 `L()`：本文件里 `import line_tool as L`，`L.fk` 会被覆盖，
> 界面在第一次刷新时静默冻结（窗口还在，状态栏空、地图不刷新）。踩过。

## 机械臂拆下来之后

`/CurrentAngle` 会返回空关节列表，界面显示 `No arm pose; check /CurrentAngle`，
按 Start 会直接退出。**这是正常的**，不是故障——底盘和相机都不受影响。

## 常量

| 常量 | 值 | 依据 |
|---|---|---|
| `LASER_TO_J7` | 0.159 m | 雷达原点 base_link `(-0.03, 0, 0.13)`，j7 轴 `+0.129` |
| `FRONT_HALF_ANGLE` | 6° | 雷达倒装，车头在激光系 180° |
| `MAX_STEP_DEG` | 6° | 单条命令最多走 6°，大了会过冲 |
| 笔夹紧 j9 | 158~160 | 实测 |
| 画线参数 | d 26.2 / z 16.0 → −5.5 | 线长 21.5 cm，底端在安装面上方 2.5 cm |

这一期只要求**流程跑通**：线画出来、进度条走完、导师认可。线宽和直线度没有
量化，导师计划后面换更高精度的传感器再做，所以弹簧笔架、接触距离标定都
不在本期范围内。
